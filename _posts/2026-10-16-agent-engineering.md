Agent 的核心循环，一张餐巾纸就能画完：LLM 思考 → 调工具 → 看结果 → 再思考，直到任务完成或认输。这就是 ReAct，2022 年的论文，现在每个 Agent 框架的骨架都长这样。

我这一年折腾 Agent 框架（自己写过一版 [agentgo](https://github.com/Hunte123)，也深度使用各类生产级 Agent）之后想说的实话是：**这个循环本身毫无难度，一个下午就能写完。Agent 工程的全部难度，都在循环之外。**

## 难点一：上下文是稀缺资源，预算要精打细算

LLM 的上下文窗口看着很大（128K、1M），但**有效的注意力远小于标称窗口**。塞得越满，中间内容被忽略得越厉害（lost in the middle）。

所以 Agent 的上下文管理本质上是个**内存管理问题**：

- **工作区文件**：长期知识落盘，按需读取，不常驻上下文
- **分层记忆**：会话历史（短期）、结构化笔记（中期）、提炼过的长期记忆（常驻）
- **及时裁剪**：工具输出该截断就截断，一个 5000 行的日志文件读进来，这轮对话基本废了

判断一个 Agent 框架成熟度，先看它怎么管上下文，而不是支持多少个工具。

## 难点二：可靠性是乘法，不是加法

单步工具调用 95% 可靠，听起来不错。但一个任务链 10 步，端到端成功率是 0.95¹⁰ ≈ **60%**。再长一点的任务，指数衰减直接击穿底线。

所以工程上要做的不是"祈祷每步都对"，而是**把乘法拆回加法**：

1. **幂等设计**：工具调用失败重试，不能有副作用叠加（发消息发三遍是事故）
2. **检查点**：多步任务分阶段提交，失败从断点恢复，而不是从头再来
3. **自校验**：让 Agent 用只读工具验证自己的产出（文件写完了吗？编译过了吗？）
4. **人闸门**：不可逆操作（删除、对外发布）前面放人工确认，这不是降低自动化程度，是把失败半径截断

我的实践红线：**任何 Agent 都不该有"删库"权限，任何对外动作都要过确认**。这不是保守，是事故复盘换来的行业共识。

## 难点三：工具设计是被低估的手艺

同一个能力，接口设计好坏，Agent 表现天差地别。几条铁律：

- **一个工具做一件事**。"管理文件"是个模糊动词，"读文件/写文件/列目录"才是三个好工具
- **返回要短而结构化**。给 Agent 塞一整个 HTML，不如给它提取好的字段
- **错误信息要能指导下一步**。"权限不足"不如"权限不足：需要 X 权限，运行 Y 命令获取"
- **宁多一个精确工具，不要一个万能模糊工具**。LLM 选工具靠描述匹配，粒度细反而选得准

写好工具描述的功夫，约等于写好 API 文档的功夫，但收益直接体现在 Agent 的成功率上。

## 难点四：任务分解与隔离

复杂任务直接丢给一个 Agent 上下文循环，很快就会糊掉。生产的做法是**父 Agent 做调度，子 Agent 做执行**：

- 子 Agent 带着干净的上下文出生，只拿任务描述，不背父 Agent 的历史包袱
- 干完活，只把结论交回来，中间过程留在子会话里
- 子任务天然并行

这跟操作系统的进程模型是一个思想：隔离换稳定性。代价是父子通信要设计好——传什么、怎么传、传多少，又是上下文预算问题，绕回难点一。

## 总结

Agent 工程的真相：**循环是商品，工程是壁垒**。上下文管理、可靠性设计、工具接口、任务编排——每一项都是传统软件工程功夫在 LLM 时代的投影。会写 ReAct 循环说明你入门了，会做上面四件事，说明你能上生产。
