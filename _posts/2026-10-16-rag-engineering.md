五十行代码就能跑一个 RAG demo：文档切块、调 embedding API、塞进向量库、检索、拼 prompt。面试题级别的流程人人会写。但 demo 和"能上线给人用"之间，隔着我在写 [ragkit](https://github.com/Hunte123) 过程中踩过的五个坑。

## 坑一：分块策略决定上限

最常见的是固定长度切块（比如 512 token，重叠 50）。它的问题不是"不优雅"，而是**语义被腰斩**：一个完整论证被切成两半，前半在 chunk A，后半在 chunk B，检索命中了 A，LLM 拿到的是残缺论据。

我的实践排序：

1. **结构优先**：有标题层级的文档（Markdown、网页）按标题切，天然对齐语义单元
2. **段落次之**：无结构文本按段落聚合，块内达到 token 上限就断
3. **重叠兜底**：块间保留 10-15% 重叠，牺牲存储换召回

另一个反直觉的点：**块不是越大越好**。块太大，单块的 embedding 会被稀释成"什么都像一点"，检索精度反而下降。512-1024 token 是比较稳的区间，具体以评估结果为准。

## 坑二：纯向量检索不够，要混着来

向量检索擅长"意思相近"，但有个盲区：**精确匹配的query**。用户问"RFC 7231 说了什么"，向量检索可能返回 RFC 7234 的段落——语义相近，但不是用户要的那篇。

所以能用的 RAG 基本都是混合检索：

```
score = α × 向量相似度 + (1-α) × BM25 分数
```

BM25 负责精确词命中，向量负责语义泛化，α 在评估集上调。工程上不用自己写 BM25，很多向量库（Milvus、Qdrant）原生支持，ragkit 里我接的是混合管道。

## 坑三：元数据过滤是被低估的杠杆

检索之前先过滤，比检索之后再过滤有效得多（预过滤 vs 后过滤，我的 govector 里也实现了两种模式）。

典型场景：知识库有 50 个产品的文档，用户问 A 产品的配置项。不过滤，top-k 里可能混进 B 产品的同名配置，LLM 一本正经地答错。一个 `product == "A"` 的预过滤，召回质量立竿见影。

**给每个 chunk 打好元数据（来源、日期、产品线、权限级别）的价值，不亚于 embedding 本身。**

## 坑四：没有评估集，一切调优都是玄学

换了个分块大小，"感觉"回答变好了——这种判断毫无意义。RAG 调优的前提是一个 golden set：

- 几十条真实问题 + 标准答案 + 应命中的原文位置
- 指标分两层：**检索层看 recall@k / MRR，生成层看答案正确率**

先测检索再测生成，定位问题在哪一层。九成"RAG 答得差"的问题出在检索层——上下文里根本没有正确答案，LLM 巧妇难为无米之炊。

## 坑五：重排（rerank）是性价比最高的一步

向量检索的 top-50 → cross-encoder 重排 → 取 top-5 喂给 LLM。

Cross-encoder（比如 bge-reranker）把 query 和文档拼在一起过模型，精度远高于双塔的 embedding 相似度，代价是慢——所以只对候选集前几十条做。这一步通常能把端到端准确率拉高 5-10 个点，是整个 RAG 管道里 ROI 最高的组件，没有之一。

## 总结

RAG 的架构图很简单，简单到让人以为周末就能上线。真正的复杂度藏在数据侧：**切块、元数据、评估集**——全是脏活，但全是护城河。模型三个月一换代，你对数据的处理管线不会。
